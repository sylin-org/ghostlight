# E5: Website and directory surfaces

## Outcome

Give the live-site source and discovery metadata the same warm, current 0.8 story as the product
repository, without publishing before owner confirmation.

## Required work

1. Obtain or open `sylin-org/website`, create a non-publishing work branch, read its agent and build
   instructions, and preserve unrelated work.
2. Update the Ghostlight page and any repeated portfolio/project data that currently exposes stale
   version, topology, store, platform, or install claims.
3. Keep the first screen compact: product truth, fit, visible/local experience, one proof, and one
   install action. Keep the language warm and inviting.
4. Update the architecture illustration to the current three executable roles without making
   process topology the hero.
5. Add or refresh the four proof recipes and accessible media where the site structure supports
   them. Every image or GIF needs useful alt text or a short transcript.
6. Reconcile page title, description, canonical URL, structured metadata, social card, and internal
   portfolio links around `Ghostlight MCP` or `Ghostlight browser automation` where qualification
   improves discovery.
7. Preserve the existing install-guide and public-status fallback synchronization owned by
   `scripts/publish-website.ps1`. Do not fork those facts into hand-maintained site copy.
8. Prepare synchronized drafts for npm metadata, MCP Registry description, Chrome Web Store copy,
   Glama, mcpservers.org, Cline, awesome-mcp-servers, Codex/Zed showcases, and other active
   directories from the E2 copy kit.
9. Account for review cost: do not resubmit Chrome copy while 0.8 is pending unless the owner
   explicitly chooses to reset or extend the review.

## Acceptance

- Website tests and production build pass locally.
- No unrelated Sylin project page emits stale Ghostlight version or topology copy.
- The site still answers fit, anti-fit, first success, current state, and local ownership.
- Package and directory drafts share one factual core but fit their field limits.
- Product and website commits are recorded separately in the ledger.
- No publishing branch is pushed or merged without explicit confirmation.

## Boundaries

Do not introduce website analytics, a feedback beacon, a CMS, or client-side version fetching
beyond the existing public-status design. Do not use external scores as hero copy.
