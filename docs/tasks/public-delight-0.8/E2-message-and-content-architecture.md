# E2: Message and content architecture

## Outcome

Turn E1 evidence into one warm canonical story and a compact copy kit that every later surface can
adapt without drifting.

## Required work

1. Create `docs/design/public-message-0.8.md` containing:
   - the one-sentence product truth;
   - a short, medium, and long description;
   - the six ADR-0100 outcome pillars;
   - audience routes for user, integrating agent/client, contributor, and trust reviewer;
   - fit and anti-fit language;
   - a claim-to-evidence matrix;
   - page-title, search-description, and social-card copy using a qualified Ghostlight identity;
   - copy for 15-second recognition, 2-minute fit, 5-minute first success, and recovery; and
   - banned overclaims and stale phrases.
2. Define one primary job for website, README, install guide, agent guide, Trust Center, changelog,
   troubleshooting, package metadata, store listing, and directories.
3. Design four proof recipes: safe form, authenticated work, browser-created-tab continuity, and
   workflow diagnosis. Use copyable prompts and name what the user should see.
4. Draft one canonical 250-character directory description and one fuller description. Do not
   publish them.
5. Keep protocol dates and architecture available below the product story. Include exact local
   stdio compatibility wording for `2025-11-25` and `2026-07-28`.

## Acceptance

- The opening describes a useful outcome before architecture, licensing, or governance.
- The language is warm without superlatives, urgency, or mascot voice.
- A reader can tell when Playwright MCP, Chrome DevTools MCP, or a first-party integration is the
  better choice.
- Every material claim points to E1 evidence or a canonical in-repo owner.
- No public surface is asked to carry every detail.

## Boundaries

The copy kit is internal design material. It does not authorize external publication. Do not add a
new content generator or move Trust Center ownership into the message document.
