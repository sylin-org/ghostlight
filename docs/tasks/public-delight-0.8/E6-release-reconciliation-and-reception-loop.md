# E6: Release reconciliation and reception loop

## Outcome

Deliver a verified, owner-reviewable 0.8 publication packet and a small local process for learning
from real use after release.

## Required work

1. Re-run E1's evidence checks immediately before publication. Update any changed version, review,
   score, directory, or competitor fact.
2. Run repository, website, package, store, registry, directory, compatibility, and link
   reconciliation against the candidate release.
3. Verify the four proof recipes through the real Ghostlight stack. At least the safe first task
   and browser-created-tab task must use a live supported client and visible browser.
4. Assemble one owner review packet containing:
   - exact product and website commits;
   - test and live-proof evidence;
   - each proposed external change and destination;
   - store-review implications;
   - remaining platform or client caveats; and
   - the ordered publication and rollback/recovery steps.
5. Stop for explicit owner confirmation before any release, website deployment, store action,
   registry publication, directory edit, discussion, showcase edit, or social post.
6. After authorized publication, run online surface checks and record the live URLs and timestamps.
   Recheck cached directory and search surfaces after 48-72 hours.
7. Create a dated, manual reception snapshot at release, 7 days, and 30 days using public counters,
   owner-visible store dashboards, support outcomes, and voluntary conversations.
8. Draft a GitHub Discussion prompt asking for client, task, where the person hesitated, what
   delighted them, and what recovery was unclear. Publication remains owner-gated.
9. Turn recurring confusion into documentation, doctor, or product follow-up with separate issue
   or ADR scope. Three reports of the same first-use failure are a stop-and-fix signal before a
   broader launch.

## Acceptance

- Every live surface agrees on public version, adapter state, supported platforms, MCP revisions,
  install command, and canonical URL.
- No release claim depends on unpublished source behavior.
- Cached surfaces are checked rather than assumed refreshed.
- Reception reporting separates human evidence from automation-prone counters.
- Quotes have explicit permission.
- No telemetry, tracking parameter, automatic review prompt, or vendor-bound reporting path exists.
- `LEDGER.md`, `docs/STATUS.md`, and relevant project memory are current when the batch closes.

## Boundaries

Owner confirmation for one publication action does not authorize every other destination. Record
the exact approved scope. A release tag or website deployment is not implied by approval to prepare
copy.
