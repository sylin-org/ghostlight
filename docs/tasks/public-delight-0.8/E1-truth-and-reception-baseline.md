# E1: Truth and reception baseline

## Outcome

Create one dated evidence map of what Ghostlight can truthfully claim, what is publicly visible,
how it is discovered, and what reception evidence actually exists before changing public prose.

## Required work

1. Re-read the canonical product facts: `docs/public-status.json`, `CHANGELOG.md`,
   `compatibility.json`, the live tool registry, supported-client installer code, platform proof,
   MCP conformance evidence, and current Trust Center claims.
2. Create `docs/research/public-reception-2026-08.md` with source URLs and observation dates for:
   - npm current version and 7-day/30-day downloads;
   - Chrome Web Store public version, users, rating, written reviews, and pending review state where
     the owner dashboard is required;
   - GitHub stars, forks, issues, discussions, release downloads, and available traffic;
   - Glama grades, favorites, per-tool grades, and stale content;
   - MCP Registry and directory status;
   - independent mentions, reviews, and user-authored workflows; and
   - search results for `Ghostlight MCP`, `Ghostlight browser automation`, and the extension name.
3. Label every signal as product evidence, distribution evidence, or reception evidence.
4. Record uncertainty. Do not turn an unavailable metric into zero.
5. Add a current capability map organized by user outcome, not tool count.
6. Recheck the closest primary-source alternatives: Playwright MCP, Chrome DevTools MCP, relevant
   first-party browser integrations, and any newer local-browser MCP entrant. Record only the
   distinctions Ghostlight can defend.
7. Reconcile stale facts in `docs/business/DISTRIBUTION.md` and
   `docs/business/DIRECTORY-SUBMISSIONS.md` when authoritative evidence is available. Do not post
   updates externally.

## Acceptance

- Every numeric or status observation has a date and direct source.
- Project-authored distribution is not called user reception.
- npm counts carry the automation caveat.
- No independent review is invented from the absence of criticism.
- The map explicitly identifies public-surface staleness and the owner of the correct fact.
- `LEDGER.md` contains the baseline date, commit, and any metrics that require owner dashboard
  access.

## Boundaries

This is research and truth reconciliation. Do not rewrite the README, website, or tool definitions
in E1. Do not request reviews, create discussions, or contact directory maintainers.
