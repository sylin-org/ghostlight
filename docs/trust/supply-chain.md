# Ghostlight Supply Chain

This page is the supply-chain evidence a reviewer needs: how releases are built and attested,
what a software bill of materials covers, the dependency posture, and how changes reach a
release.

## Releases

Published releases use verifiable artifacts. Each payload artifact is covered by the release's
SHA-256 manifests so you can confirm you received exactly what was published, and each release
includes keyless Sigstore build-provenance attestations that tie the artifacts back to the
exact source commit and workflow run that produced them (attestation coverage spans every
release asset from 2026-07 onward; earlier releases attest the packaged archives). Releases
also carry a canonical `SHA256SUMS` manifest. A read-only assembly job creates the complete
release bundle, including the SBOM; the privileged publisher can only download that bundle,
verify its exact file list and hashes, attest it, and create the release.
The public service channels currently serve 1.3.14. The Chrome Web Store adapter serves 1.3.12 and
is compatible with that service release under adapter protocol 3.
The workflow builds and attests a complete candidate without publishing it; channel publication
remains an explicit owner-approved operation after verification. WinGet metadata is
prepared only against observable matching assets. See
[the current build-only workflow](../../.github/workflows/release.yml) and
[SECURITY.md](../../SECURITY.md).

## Verify a release

A 2.0 release publishes these files:

- `ghostlight-<target>`, `ghostlight-service-<target>` and `ghostlight-desktop-<target>` for
  `x86_64-pc-windows-msvc` (with `.exe`) and `x86_64-unknown-linux-gnu`;
- `ghostlight-v<version>-x86_64-pc-windows-msvc.zip`, the WinGet archive;
- `ghostlight-extension-v<adapter version>.zip`, the extension package;
- `ghostlight-<version>.tgz`, the npm launcher;
- `ghostlight-v<version>.mcpb`, the Claude Desktop bundle;
- `ghostlight-v<version>-sbom-<crate>.cyclonedx.json`, one per workspace crate;
- `release-candidate.json` and `SHA256SUMS`.

Download `SHA256SUMS` into the folder that holds the files you fetched, then check them:

    sha256sum -c SHA256SUMS --ignore-missing
    gh attestation verify <file> --repo sylin-org/ghostlight --signer-workflow sylin-org/ghostlight/.github/workflows/release.yml

The first prints `OK` for each file you downloaded that matches its line in `SHA256SUMS`. On
Windows, `(Get-FileHash <file> -Algorithm SHA256).Hash` computes the same SHA-256 to compare with
that line. The second, using the GitHub CLI, proves the file was built by this repository's
release workflow and prints the source commit and workflow run that produced it.

## SBOM

The release candidate includes CycloneDX component SBOMs generated by the release workflow, one
for each Rust workspace package. They use
`ghostlight-v<version>-sbom-<component>.cyclonedx.json` beside the artifacts and checksums. Releases
through v0.5.4 predate the SBOM work and carry no SBOM asset.

## Dependencies

The dependency tree favors fewer, well-understood crates over broad transitive graphs. Managed
policy signatures use pure-Rust Ed25519 and ML-DSA-65 implementations. HTTPS uses rustls with the
pure-Rust ring provider; the current feature set does not pull in aws-lc or another C crypto
provider. No formal export classification (ECCN) has been made; the cryptographic source is public
in this repository. As a dated data point, the npm
package scored 100/100 on all axes on Socket.dev at publication (2026-07); see
[the npm package](https://www.npmjs.com/package/ghostlight). That is a snapshot of that
moment, not a standing guarantee, and the SBOM above is the authoritative, per-release
dependency record.

## Build and change management

Design decisions are recorded in ADRs. CI gates formatting, warnings-denied linting, Rust and
extension tests, process journeys, dependency policy, and release metadata. Release binaries use
checksums and keyless build-provenance attestations tied to the source commit and workflow run.
Customer policy-signing keys belong to the customer and never enter Ghostlight source, releases,
or CI. Compromise of the release pipeline remains the residual binary supply-chain risk covered by
the best-effort advisory target in [SECURITY.md](../../SECURITY.md).

See [security-overview.md](security-overview.md) for the vendor-side security posture.
